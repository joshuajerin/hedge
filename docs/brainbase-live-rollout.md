# Brainbase live rollout: fast, visible, paper-only handoffs

This is a **deployment and integration checklist**, not a claim of live deployment. The checked-in Brainbase configuration keeps the seven existing cloud agent IDs, `gemini-3.8-flash`, `kafka`, and all eight existing edges. No order execution is delegated to Brainbase. The configured DAG is CIO -> Market Scout / Trend Analyst / News Analyst; all three -> Portfolio Manager; Portfolio Manager -> Backtester -> Risk Reviewer. Scout can inform Trend/News through the existing routed work, but do not add undeclared edges or pretend a graph edge guarantees a result.

## Fast conversational path and visible progress

1. The local Slack bridge admits only approved inbound CIO mentions, persists its canonical `run_id`, workspace, channel, and root thread, and handles its deterministic Tier-0 greetings locally. CIO answers other simple conversation directly without waiting for a research fan-out. A verified direct CIO artifact, if transport supports one, is `hedge.cio-result.v1` with exactly `schema_version`, `run_id`, `workspace_id`, `channel_id`, `root_thread_ts`, `role: cio`, `status: COMPLETED`, `text`; the trusted result adapter alone delivers it in the same root thread.
2. **Ingress mismatch:** the current `slack_bridge.format_cio_task` sends `hedge.slack-request.v1` with `slack.mention_text`, thread context and `delivery` correlation; it does **not** send a typed `hedge.research-request.v1`, symbols, deadline, or parent hashes. The CIO can classify and prepare an answer from that real ingress, but the *trusted adapter* must verify stored `SlackState` affinity, derive a truthful research objective/scope, allocate deadline/artifact ID, and create the typed request. Without this wiring, no typed handoff chain can honestly be claimed. For research with that adapter in place, create a typed request and start the relevant specialists promptly. With a known ticker universe, Scout/Trend/News can research concurrently; when the universe is unknown, Scout supplies candidates before Trend/News rank them concurrently. This scheduling is an adapter/orchestration responsibility, not a guaranteed Brainbase scheduler SLA. Use one persisted deadline for the entire run (a 60–120-second research budget may be a starting operational target, subject to measured latency). Reserve time for Portfolio, Backtest, Risk, provenance validation, and delivery. Stop waiting at the deadline. There is no unlimited polling or fabricated specialist completion.
3. The *trusted bridge* may post a short accepted/working acknowledgement or role-attributed progress in the canonical Slack thread when explicitly wired, with stable delivery IDs and fixed role credentials. These prompt changes do **not** wire such progress or authorize autonomous posts by agents. The local bridge currently has `:eyes:`/`:brain:` lifecycle reactions; those do not prove specialist completion. Do not claim a specialist has replied until its real authenticated task-bound result is validated. A partial user-facing report must clearly distinguish verified findings from pending/unavailable work and HOLD. If the available result transport cannot safely deliver it, record HOLD/unsupported for operator handling instead of posting an invented answer.

## Exact typed handoffs

The *trusted local adapter*, not model text or a Slack message, supplies run/task identity, canonical root, timezone-aware timestamps, unique artifact IDs, stage role/status, and computed parent SHA-256 hashes. Every `hedge.orchestration_protocol` artifact has exactly these shared fields: `schema_version`, `artifact_id`, `run_id`, `workspace_id`, `channel_id`, `root_thread_ts`, `role`, `created_at`, `deadline_at`, `parent_hashes`, `status`. Unknown or missing fields, wrong role/status, stale run, cross-thread affinity, duplicate/noncanonical parent hashes, or late results fail closed. Canonical hash is SHA-256 of UTF-8 sorted-key compact JSON (`artifact.sha256()`); the local adapter independently recomputes and validates the full chain.

| Stage | Exact schema / role / status | Extra fields and required parent |
| --- | --- | --- |
| Research mandate | `hedge.research-request.v1` / `research_coordinator` / `REQUESTED` | `objective`, nonempty `symbols`, nonempty `research_questions`; no parents. If no verified nonempty symbol/scope is available, this strict schema cannot be constructed; request clarification or HOLD instead of inventing a symbol. |
| Scout/Trend/News | `hedge.specialist-report.v1` / `specialist` / `COMPLETED` | `specialty` = fixed `market_scout`, `trend_analyst`, or `news_analyst`; `summary`, nonempty `findings`, finite `confidence` in [0,1]; parent includes request hash. Missing work is **not** a completed report. |
| Portfolio | `hedge.portfolio-draft.v1` / `portfolio_manager` / `DRAFT` | `thesis`, nonempty `target_allocations` strings; parents include **every actual** specialist report hash. Paper allocation only. |
| Backtest | `hedge.backtest-report.v1` / `backtester` / `COMPLETED` | `period`, `summary`, boolean `passed`; parent includes portfolio draft hash. `passed: false` means no qualifying backtest. |
| Final risk sidecar | `hedge.risk-review-attestation.v1` / `risk_reviewer` / `APPROVED`, `HOLD`, or `REJECTED` | `rationale`, `decision`, `decision_sha256`; parent includes backtest report hash. Only APPROVED may carry a strict complete `hedge.decision.v1` and its matching canonical SHA-256. HOLD/REJECTED use null decision and null hash. |

The validated CIO `hedge.handoff-chain.v1` result includes exactly `schema_version`, `request`, `reports`, `draft`, `backtest`, `attestation`, and `text`. At least one real specialist report is required, and `validate_handoff_chain` binds all parents and canonical root. No full chain can be produced when an indispensable stage is missing. A HOLD/REJECTED risk sidecar still requires a real prior draft and backtest; when work stops earlier, show only authenticated partial findings if a suitable trusted result path exists, otherwise record a terminal failure/HOLD for operator review. Never synthesize typed stages to satisfy a schema. Keep the attestation as **JSON sidecar**, while the chain's `text` is the separate human-facing reply; Risk Reviewer must not append prose to JSON or post a bare decision to Slack. The separate real-time CIO inference response remains its own strict `hedge.cio-inference-response.v1` contract, never the Slack reply.

## Trust and delivery blockers

`BrainbaseResultConsumer` runs inside the local CIO Slack bridge. It persists the verified CIO task ID and checks `task get --json` on a bounded interval. A successful task may produce a clearly labeled **unreviewed CIO research draft** from its own completed assistant transcript; missing or ambiguous output gets an explicit unavailable notice. Brainbase CLI task/log output does not document an authenticated structured terminal artifact, so this draft is never a specialist report, Risk approval, or paper decision. Do not advertise live specialist delivery. That needs trusted task-bound child artifacts, validated hashes and fixed-role credentials in the original Slack thread. Model output must never select the destination, profile, or token. See [result delivery](brainbase-result-delivery.md), [protocol](orchestration-protocol.md), and [Slack roles](slack-multi-profile.md).

Seven distinct Slack bot profiles are specified, with the CIO as the only inbound Socket Mode app and six specialists outbound-only. Brainbase manifests currently declare `capabilities.slack: true`, but `brainbase agent connections --json` reports all seven cloud agents' Slack integrations disconnected. This capability flag does not install a Slack app or grant a working connection. The local CIO bridge has its own Slack token. The trusted adapter alone may use fixed-role specialist tokens after app install, channel membership, authorization, and task-result verification. No token belongs in a prompt, task, manifest, or result. The local paper runner remains outside this research workflow; even an APPROVED risk attestation is a **paper proposal**, not proof of order submission or authorization to call IBKR. Do not treat model output as executable code or an execution request.
